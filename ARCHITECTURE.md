## Boundaries

**Frontend (`web/`).** Owns all invitation *editing* state, all browser storage, and the guest and
host UIs. It reaches the backend through exactly one module — `web/src/api.ts` — which issues
`fetch` calls to relative `/api/*` paths; in dev, `web/vite.config.ts:8-10` proxies `/api` to
`localhost:3001`. Screens (`App.tsx`, `GuestPage.tsx`, `ManagePage.tsx`, `LandingPage.tsx`) compose;
state lives in `web/src/hooks/`. `web/src/types.ts:1` is a **hand-written mirror** of the server's
zod schemas, not a generated or shared artifact — a deliberate constraint, not an omission:
NFR-8 (`docs/03-non-functional-requirements.md:185-186`) requires the mirror to change in the same
PR as the schema.

**Backend (`server/`).** `buildApp` (`server/src/app.ts:21`) registers cors + cookie, a
`CANONICAL_HOST` redirect hook (`app.ts:46-52`), `/healthz` (`app.ts:98`), then five route modules:
auth, account, invitations, og, unsubscribe (`app.ts:109-117`). When `web/dist/index.html` exists it
also serves the built SPA from the same process and falls back to the shell for non-`/api` GET/HEAD
(`app.ts:122-142`) — so production is a single container (`Dockerfile:17-33`, `DATA_DIR=/data`).
Persistence is split: published invitations are one JSON file per id (`server/src/store.ts:1-4,26`),
and accounts/sessions live in SQLite (`server/src/db.ts`). Both assume a single process — NFR-7
(`docs/03-non-functional-requirements.md:166-181`) states the deployment must not scale above one
instance, and that RSVP appends have no concurrency control beyond process serialization.

**LLM gateway (in-process, `server/src/llm/`).** `routing.ts:55-80` is a static table of
task → primary → fallbacks; `gateway.ts:279-333` walks that list, calling Anthropic through the SDK
and every other provider through the OpenAI-compatible `fetch` adapter (`gateway.ts:219-247`,
`openaiCompat.ts`). It validates each response with `extractJson` + `schema.parse`
(`gateway.ts:310`), logs one JSON line per attempt (`gateway.ts:159-163`), and throws
`AllModelsFailedError` when the walk is exhausted. It is a library the pipeline imports — not a
network hop, not a separate process. The `gemma3-4b` fallback on all four routes
(`routing.ts:59,65,72,77`) is dev-only by construction: it resolves against `OLLAMA_BASE_URL`,
defaulting to `localhost:11434` (`openaiCompat.ts:44`), and `docs/05-deployment.md:34-35` states it
"always fails in prod — it points at a dev-machine host — and is skipped the same way" as any
unkeyed provider.

**Renderers (two, unshared).** `web/src/components/InvitationPreview.tsx:17` maps design tokens to
CSS class names defined in `web/src/styles.css:938-979`. `server/src/og/render.ts:149` builds a
satori vdom with its own hard-coded style maps (`render.ts:13-32`) and rasterizes via resvg. Grep
confirms the isolation: `og/render.ts` is imported only by `server/src/routes/og.ts:4` and its test;
`InvitationPreview` is imported only by files under `web/src` and `web/test`.

## Data flow — the generation pipeline

The pipeline is **three model calls, not five**, and only the middle two are parallel.

1. **Browser → API.** `web/src/api.ts:89` posts `{ text, source }` to `/api/invitations/generate`.
   If the host saved a BYOK key it rides as `x-llm-provider` / `x-llm-key` headers (`api.ts:76-79`).
2. **Validation + gates.** `GenerateRequest.parse` (`routes/invitations.ts:54`) enforces
   `text` trimmed, 1–500 chars, and `source` defaulting to `"direct"` (`schemas.ts:88-92`). BYOK
   headers are parsed into `{provider, key}` (`invitations.ts:344-356`); non-BYOK requests then hit
   the budget breaker (503) and per-IP allowance (429) at `invitations.ts:311-331`.
3. **Stage 1 — brief.** `generateInvitation` (`pipeline/generate.ts:13`) awaits `extractBrief`
   (`pipeline/brief.ts:13`), task `brief_extraction`. **Crossing shape:** `EventBrief` —
   `event_type`, `hosts[]`, nullable `date`/`time`/`venue`/`city`/`extra_details`, `tone`,
   `language` (`schemas.ts:11-28`). Dates stay as free text; nothing is normalized here.
4. **Stages 2 and 3 — copy ∥ design.** `Promise.all([generateCopy, resolveDesign])`
   (`generate.ts:14`), both taking `JSON.stringify(brief)` as the user message
   (`copy.ts:19`, `design.ts:19`). **Crossing shapes:** `InvitationCopy`, six required strings
   (`schemas.ts:42-51`), and `DesignTokens`, four closed enums (`schemas.ts:56-61`).
5. **Each stage → gateway.** `completeJson(task, {system, user, schema})` walks the task's route
   (`routing.ts:55-80`); output is parsed leniently then validated by the same zod schema
   (`gateway.ts:186-197,310`). Failure of every model → 502 carrying per-model `causes` as classes
   only (`invitations.ts:336-339`), which the client maps to messages (`api.ts:40-52`).
6. **API → browser.** The response body is `{ brief, copy, design }` (`generate.ts:15`) — note
   `background` is **not** in the generate response; `Invitation.background` is optional
   (`schemas.ts:76`) and only ever set by the separate `/api/invitations/background` action
   (`invitations.ts:108-144`), which is an explicit editor press, not a pipeline stage.
7. **Client state.** `useInvitationEditor` stores it (`useInvitationEditor.ts:56-57`), accumulates
   the description across turns and re-runs the whole pipeline on the combined text
   (`useInvitationEditor.ts:51`), and nudges once per session if `parseEventStart` can't read the
   date (`useInvitationEditor.ts:63-66`).

Downstream of the pipeline, publish snapshots the whole `Invitation` into
`PublishedRecord.versions[]` (`store.ts:11-18,44`), and the OG PNG is rendered lazily from the
latest version at request time, cached by `id:version` (`routes/og.ts:53-57`) in the bounded LRU at
`server/src/og/cache.ts`. Snapshots are immutable, so a cached PNG never goes stale and republishing
mints a new key rather than invalidating the old one.

## Known inconsistencies

1. **OG card is not the invitation.** It omits `body`, `rsvp_prompt` and `closing`
   (`render.ts:221-239` vs `InvitationPreview.tsx:42-47`), so what a messenger unfurls is a strict
   subset of what the guest page shows. Nothing in either test suite compares the two.
2. **OG ignores backgrounds.** `renderOgPng` destructures only `{copy, design}` (`render.ts:150`)
   and never reads `invitation.background`, while the web card composites it
   (`InvitationPreview.tsx:55-74`). An invitation with an AI background unfurls without it.
3. **Three hand-maintained copies of the token→style map** with no shared source: `styles.css:938-979`,
   `og/render.ts:13-32`, `scripts/build-design-cards.mjs`. The comment at `render.ts:10-12` states
   the sync is manual. Tests catch a *missing* entry, never a *drifted* value.
4. **`schemas.ts` is the source of truth only for request bodies and stored types.** Several
   response shapes have no zod schema and are inline object literals — publish
   (`invitations.ts:180-184,202`), the public snapshot (`invitations.ts:209-213`), and
   `/api/auth/session` (`routes/auth.ts:150-167`). Their client mirrors (`types.ts:61-71,168-181`)
   are therefore hand-matched against route code, not against a schema. They agree today.
5. **`.design-sync/previews/InvitationPreview.tsx:1` imports from `"inv-app-web"`**, but
   `web/package.json` declares no `main`, `module`, or `exports`. The import cannot resolve. The file
   is outside `web/tsconfig.json:16`'s `include` and excluded from Biome (`biome.jsonc:11`), so
   nothing catches it. `.design-sync/NOTES.md:3` acknowledges there is no library entry point.
6. **README setup contradicts routing.** `README.md:20` says to add `ANTHROPIC_API_KEY`, but the
   default primaries are Groq and Gemini (`routing.ts:57-79`) and `server/.env.example:5-11` lists
   `GROQ_API_KEY` + `GEMINI_API_KEY` as the required pair with Anthropic commented out as optional.
7. **`.palette-minimal` is deliberately asymmetric** — it alone lacks `--bg-rgb` and `--wash`
   (`styles.css:941` vs `938-943`). Coherent with `InvitationPreview.tsx:56` dropping the background
   for `minimal` and the route rejecting it outright (`invitations.ts:115-117`), so this is an
   intended asymmetry, noted here only because it looks like an omission when reading the CSS alone.
8. **`docs/04-architecture.md:12` diagrams the same Fastify topology**, so the repo's own
   architecture doc does *not* claim FastAPI or LiteLLM — the mismatch is with the task brief, not
   with the docs. That diagram is stale in one respect: line 13 shows the server calling the
   `Anthropic API` as its model provider, while the default primaries are now Groq and Gemini
   (`routing.ts:57-79`) with Anthropic as a fallback.
